# Review T1.4b (config HTTP API) - reviewer attack results
Live attack script (Sanctum cookie + CSRF flow, 5 role accounts, 6 concurrent clients): 47 checks, 42 passed on the first run.
PASS: public bundle (200, ETag, 304 on If-None-Match with empty body, no draft/audit/user leakage); 401 for anonymous, 403 for user/architect on every admin route, 200 for editor;
419 without the CSRF header; draft lifecycle with optimistic concurrency (201 + ETag, 428 without If-Match, 412 on a wrong or stale ETag, 200 + new ETag on a correct one);
invalid payload -> 422 CONFIG_INVALID with issues[]; non-object / malformed JSON / label > 120 / 3000-deep nesting / __proto__ payload -> 4xx never 500; > 1 MB -> 413;
mass-assignment fields (status, version, is_draft, payload_hash, current_version_id ...) ignored; unknown or odd keys (path traversal, SQL quote) -> 404;
publish -> 200, publish again -> 422 NO_DRAFT, bundle ETag changes; 6 concurrent draft creates -> exactly one 201; 6 concurrent publishes of one draft -> exactly one 200;
rollback to current -> 422, unknown -> 404, non-numeric -> 4xx, to oldest -> new linear version whose payload equals the old one; audit rows carry request_id and no IP/user-agent/email/password; discard -> 204; write rate limit -> 429.
Findings: (1) REAL BUG fixed: `GET .../versions/99999999999999999999` returned 500 (integer overflow in the DB query) -> route constraint limited to 9 digits and rollback `version` capped (`max:999999999`);
(2) `%00` in the key returns 400 (accepted: the web server rejects NUL); (3) two failures were the config-write rate limit (30/min per user) doing its job during the stress run; re-tested after the window: all pass.

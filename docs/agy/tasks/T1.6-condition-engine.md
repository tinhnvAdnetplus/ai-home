# TASK T1.6 — Condition evaluator + wizard state resolution (TASKS.md row 1.6, plus the core of 2.4)

Goal: given a validated wizard config and the customer's answers so far, decide which fields are visible / disabled / which options are disabled, and drop answers
of hidden fields (cascading). Pure TypeScript inside `packages/config-schema` (no React, no network, no `eval`/`Function`). The condition AST and its validation already exist
(`src/condition.ts`, `src/condition-types.ts`, `collectConditionVars`); read them and `docs/config-schema.md` first. Extend `docs/config-schema.md` with a "Condition semantics" section.

## Semantics (strict on purpose — NOT JavaScript/JSON-Logic coercion). Document them exactly in the docs.
- Values: an answer is `string | number | boolean | null | string[]`. Anything else (objects, NaN, Infinity, functions, nested arrays, >100-item arrays, strings >2000 chars) is treated as `null`.
  Missing answers and `undefined` are `null`.
- `{ var: key }` reads ONLY an own property of the answers object (`Object.hasOwn`); inherited/prototype keys are never read; a throwing getter yields `null`.
- `==` / `!=`: strict equality for scalars, no coercion (`1 == "1"` is false, `true == 1` false, `null == missing` true). Arrays are compared element by element in order (strict).
- `<`, `<=`, `>`, `>=`: true only when BOTH sides are finite numbers and the relation holds; otherwise `false` (strings/booleans/null/arrays never compare).
- `in`: `{ in: [needle, haystack] }`; haystack is an array literal or a var resolving to `string[]`/array of scalars -> true iff some element is strictly equal to the needle.
  A scalar needle against a `string[]` answer works (checkbox groups). If the haystack is not an array the result is `false` (NO substring matching).
- `and` / `or`: boolean results over truthiness; `!`: boolean negation of truthiness. Truthiness: `false`, `null`, `0`, `NaN`-like, `""`, `[]` are falsy; everything else truthy.
- Top-level literal/var conditions are coerced by truthiness; `evaluateCondition` always returns a boolean.

## Deliverables (`packages/config-schema/src/...`, kebab-case files, < 150 loc each, named exports, no `any`/`as`)
1. `evaluateCondition(condition: Condition, answers: Readonly<Record<string, unknown>>): boolean` — total function (never throws for any `Condition` value and any answers object, including
   `Object.create(null)`, frozen, hostile getters). Guard recursion depth (<= 8) and node count (<= 80) defensively and return `false` beyond them.
2. `evaluateConditionSafe(input: unknown, answers: unknown): { ok: true; value: boolean } | { ok: false; reason: 'INVALID_CONDITION' | 'INVALID_ANSWERS' }` — parses the condition with the existing schema first.
3. `resolveWizardState(wizard: WizardConfig, answers: Record<string, unknown>)` returning
   `{ visible: Record<string, boolean>; disabled: Record<string, boolean>; disabledOptions: Record<string, readonly string[]>; answers: Record<string, unknown>; missingRequired: string[] }` where
   - a field is visible iff its `visibleWhen` is absent or true; fields in a hidden step/section are NOT special (visibility is per field);
   - `disabled` comes from `disabledWhen`; `disabledOptions[field]` lists option values whose `disabledWhen` is true; a currently selected disabled option is removed from the answer (for `checkbox_group`) or the answer is dropped (single choice);
   - **cascade**: hiding a field removes its answer, which can change other conditions; iterate to a fixpoint (config validation guarantees no cycles, still cap at `fields + 1` passes) and make the result independent of field order;
   - hidden fields never appear in `answers` (pruned copy; the input object is NEVER mutated; keys not in the wizard are dropped);
   - `missingRequired`: keys of visible, non-disabled, `required` fields whose answer is empty (`null`, `""` after trim, `[]`); `boolean` required fields count as answered when `true`/`false`.
4. Exports in `src/index.ts`; an `AnswerValue` type and `normalizeAnswer(value: unknown): AnswerValue` helper (the "treated as null" rules above).
5. Docs section + a short example in `docs/config-schema.md` (e.g. choosing 平屋 hides "second-floor toilet" and removes its stale answer).

## Tests (Vitest + fast-check, in the package; deterministic, no time/network)
- Truth tables for every operator with valid arity: strict equality matrix (1 vs "1", true vs 1, 0 vs false, "" vs null, null vs missing, arrays equal/unequal/different order), comparisons with numbers, with strings (false), with NaN/Infinity (false), `in` with array literal, with `string[]` var, with scalar var (false), with missing var (false), with string haystack (false, no substring match).
- Truthiness table for and/or/! and top-level literal/var.
- `var`: own vs inherited (`toString`, `constructor`, `__proto__` through `Object.create`), `Object.create(null)`, frozen answers, throwing getter, Proxy that throws -> never throws.
- `evaluateConditionSafe`: invalid AST (unknown operator, depth 7, 61 nodes, two keys) -> `INVALID_CONDITION`; answers not an object -> `INVALID_ANSWERS`.
- `resolveWizardState`: the sample wizard; a hand-built cascade A -> B -> C (hiding A hides B hides C and removes all three answers); the 平屋/2階建 example (floors answer toggles a second-floor field and a disabled option);
  disabled option removed from a checkbox answer; stale unknown keys dropped; required-missing for each field type; input never mutated (deep-freeze); idempotent (`resolve(resolve(x).answers)` equals `resolve(x)`); order independence (shuffle fields -> same result);
  performance: 150 fields forming a dependency chain resolves in < 50 ms.
- Property tests (`fc.assert`, >= 200 runs): for arbitrary valid conditions (build an arbitrary of the AST within limits) and arbitrary answers (`fc.anything`-like mix): never throws; deterministic; `evaluate(!c) === !evaluate(c)`;
  `evaluate(!(a and b)) === evaluate(!a or !b)`; `evaluate(a or b) === evaluate(b or a)`; answers untouched.

# TASK T1.1 — `packages/config-schema`: the single source of truth for admin-managed configuration (TASKS.md rows 1.1 + part of 1.6)

Goal: everything an admin can configure is described by Zod schemas in ONE shared TypeScript package. The wizard (questions the customer answers)
is the first and most important config type. Later tasks will: export JSON Schema for PHP validation (1.2), store/publish versions (1.3-1.4),
load it in React (1.5), evaluate conditions (1.6), and build the admin editor (1.8). This task builds the schemas + validation + defaults + tests.
No database, no API, no UI in this task.

### Part B — primitives (`src/primitives.ts`, `src/condition.ts`)
- `localizedTextSchema`: object with `ja` REQUIRED (trimmed, 1..500 chars) and optional `en`, `vi` (same limits); no other language keys (strict). Unicode safe.
- `keySchema` for field/step/section/option keys: `^[a-z][a-z0-9_]{0,47}$`, and a deny-list (`constructor`, `prototype`, `hasownproperty`, `tostring`, `valueof`, `proto`...)
  so a key can never be used for prototype pollution. `bindingKeySchema`: dot.case `^[a-z][a-zA-Z0-9]*(\.[a-z][a-zA-Z0-9]*)*$`, max 64.
- `mediaRefSchema`: `{ mediaId: string (1..64, [A-Za-z0-9_-]), alt: localizedText }` (the media library comes later; this is only a reference).
- `conditionSchema` (recursive, `z.lazy`): a RESTRICTED subset of JSON Logic, stored as plain JSON (never executed as code). Allowed nodes: literals
  (string up to 200 chars | finite number | boolean | null), `{ "var": "<fieldKey>" }`, and operator objects with exactly one key among
  `and`, `or`, `!`, `==`, `!=`, `<`, `<=`, `>`, `>=`, `in` with the right arity (and/or: 1..10 operands; `!`: 1; comparisons: 2; `in`: 2 where the right side is an array
  literal of scalars (<= 50 items) or a var). Limits: depth <= 6, total nodes <= 60. Reject: unknown operators, objects with several keys, `var` with non-key strings or
  deny-listed keys, NaN/Infinity, nested arrays elsewhere. Export `Condition` type + `parseCondition`.
  (The evaluator is T1.6 — do NOT implement evaluation here, but expose `collectConditionVars(condition): string[]` used for cross-validation.)

### Part C — wizard schema (`src/wizard/*`)
Structure `wizardSchema`: `{ schemaVersion: 1, steps: Step[] }`, `Step = { key, title, subtitle?, icon?, sections: Section[] }`,
`Section = { key, title, description?, fields: Field[] }` (all texts are `localizedText`; `icon` is a key from a small allow-list const `STEP_ICONS` such as
home, map-pin, layout-grid, users, image, plus a few more).
`Field` = discriminated union on `type`, all sharing: `key`, `label`, `help?`, `required: boolean` (default false), `visibleWhen?: Condition`, `disabledWhen?: Condition`,
`binding?: bindingKey` (maps the answer to a planner constraint; see registry below), `summaryLabel?`. Types:
`text` (maxLength 1..500, placeholder), `textarea` (maxLength 1..2000, showCounter), `number` (min, max, step > 0, unit key, defaultValue, `allowedUnits?` e.g. ['tsubo','m2'] ),
`range` (min,max,step,unit), `select` / `radio` (options), `checkbox_group` (options, minSelected?, maxSelected?), `image_select` (options with `image: mediaRef`, `multiple: boolean`),
`boolean`, `upload` (accept: list of mime types from an allow-list, maxFiles 1..10, maxSizeMb 1..20).
`Option = { value: key, label, description?, image?: mediaRef, disabledWhen?: Condition }`. `defaultValue` is typed per field type.
Limits (to protect the system): steps <= 20, sections per step <= 20, fields total <= 150, options per field <= 60, texts as above.
**Binding registry** `src/binding-registry.ts`: a typed const list `{ key, valueType: 'number'|'string'|'boolean'|'string[]', description }` of the planner inputs
that exist today. Derive it from the fields tagged for the plan in `../old-version/js/form-schema.js` and how `../old-version/js/planner.js` reads them (land area, frontage, depth,
road side, floors, target area, LDK size, number of children rooms, tatami room, parking count, budget...). Keep it small and accurate; every key gets a description. This registry is
CODE (planner capabilities), the config only references it.

### Part D — validation (`src/wizard/validate.ts`) and API
`parseWizardConfig(input: unknown): { ok: true; data: WizardConfig } | { ok: false; issues: Issue[] }` — never throws for any input (including `undefined`, huge objects, cyclic-looking
data, getters). `Issue = { path: (string|number)[]; code: IssueCode; message: string }` where `IssueCode` is a stable string union. Run Zod first, then cross-validation
that reports ALL problems, not just the first. Codes (at least): `SCHEMA_INVALID`, `DUPLICATE_KEY` (steps/sections/fields/options; field keys must be unique across the WHOLE wizard),
`UNKNOWN_FIELD_REF` (a condition uses a var that is not a field key), `SELF_REFERENCE` (a field's own visibleWhen/disabledWhen uses itself), `CONDITION_CYCLE` (A depends on B depends on A, through visibleWhen/disabledWhen),
`UNKNOWN_BINDING`, `BINDING_TYPE_MISMATCH` (e.g. a text field bound to a number key; duplicates of one binding in two fields are also an error `DUPLICATE_BINDING`),
`DEFAULT_NOT_IN_OPTIONS`, `DEFAULT_OUT_OF_RANGE`, `RANGE_INVALID` (min > max, step <= 0), `SELECTION_LIMITS_INVALID` (minSelected > maxSelected or > options), `EMPTY_OPTIONS`,
`LIMIT_EXCEEDED`. Messages are plain English (the admin UI will translate by code later).
Also export `serializeWizardConfig` (stable key order JSON string) and a `sampleWizard` in `src/defaults/sample-wizard.ts` (2 steps, ~8 fields, every field type once, one
condition, two bindings) used by tests and docs. It is NOT the production STEP 1-5 form (that is task 2.6).
`src/index.ts` exports the public API with named exports only. Write `docs/config-schema.md` (English): the model, limits, every issue code with an example, and how later tasks use the package.

## Tests (Vitest inside the package; use fast-check for the property tests)
- sample wizard is valid and round-trips (`parse(JSON.parse(serialize(x)))` equals x); serialization is deterministic.
- one minimal failing config per issue code above, asserting `ok: false`, the exact `code` and a sensible `path`; a config with several problems reports all of them.
- localizedText: ja required, empty/whitespace-only rejected, 501 chars rejected, unknown language key rejected, Japanese/Vietnamese/emoji accepted, trimming behaviour documented.
- keys: valid/invalid samples, every deny-listed key rejected, `__proto__` / `constructor` as field key or as `var` rejected, uppercase/hyphen/leading digit rejected, 49 chars rejected.
- condition: every operator with valid arity passes; wrong arity, unknown operator, two keys in one object, depth 7, 61 nodes, NaN/Infinity, nested arrays, `in` with a 51-item array all fail; `collectConditionVars` returns de-duplicated sorted vars.
- limits: 21 steps, 151 fields, 61 options -> `LIMIT_EXCEEDED`; exactly at the limit -> ok.
- property tests: for arbitrary JSON values (`fc.jsonValue()`), arbitrary strings used as keys, and mutated copies of the sample wizard, `parseWizardConfig` never throws and returns a well-formed result;
  it never mutates its input (deep-freeze the input in the test).
- binding registry: no duplicate keys, every key matches `bindingKeySchema`, every valueType is one of the four.
- smoke test in apps/api (see Part A).

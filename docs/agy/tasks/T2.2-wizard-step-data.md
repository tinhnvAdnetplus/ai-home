## Rules that make the screen look like the mockup
- **One mockup question card = one `Section`** (title = the numbered heading, e.g. `'3. 希望する階数'`, written with `tx(ja, en, vi)`). The card shows the required/optional chip itself. A card with several controls (e.g. two dropdowns, a grid of room counts)
  has several `fields` in the same section; a single-field section hides the field label (it is read by screen readers only), a multi-field section shows each field label as a small sub-label — so give multi-field fields short, meaningful labels.
- **Pick the control type the mockup shows**: tiles with a picture/icon/colour swatch -> `image_select` (use `imgOpt(value, mediaId, ja, en, vi)`; `multiple: true` when the mockup says 複数選択可); plain radio list -> `radio`; dropdown -> `select`;
  checkbox grid/list -> `checkbox_group` (options via `opt`); free text -> `text`/`textarea` (`maxLength`, `showCounter` for the character counter); numeric entry with a unit -> `number` (unit key `'tsubo'|'m'|...` as the schema allows; use `allowedUnits` when the mockup offers a unit switch);
  file upload -> `upload`; yes/no -> `boolean`.
- Texts: `ja` copied from the mockup, plus `en` and `vi` translations. Chips `必須` (required) and `任意` (optional) must match the mockup: set `required` accordingly.
- **Option `value`s and all keys must match `^[a-z][a-z0-9_]{0,47}$`** (start with a letter, lowercase, digits and underscores only; no hyphen, no leading digit). Keys must be unique across the WHOLE wizard (also across the other steps: prefix with the step topic, e.g. `land_`, `plan_`, `life_`, `design_`). Never reuse the keys `construction_purpose, house_type, floors, family_adults, family_children, budget_range, target_area_range, house_style, notes_step1` (STEP 1 owns them).
- Conditions (`visibleWhen`/`disabledWhen`) only where the mockup implies them; the previous STEP 3 data uses `{ var: 'floors' }` compared with `'one_story'`: keep such references working with STEP 1's new values (`one_story`, `two_story`, `three_story`, `consult`).
- Bindings: use `binding: '<key>'` only when the field's value type matches the registry type (see `packages/config-schema/src/binding-registry-data.ts`; select/radio/image_select bind to `string`, `checkbox_group` to `string[]`, `number` to `number`). When in doubt leave it unbound (a mapping layer to the planner comes later) and list it under Follow-ups.

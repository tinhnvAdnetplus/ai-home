# TASK T0.6 — Authentication + roles (TASKS.md row 0.6). Requires T0.2 and T0.8 done.

Goal: users can register/log in from the React SPA (same origin) and the backend can tell who may do what.
Backend only (the React login screens come later with the admin shell).

## Design decisions (already made — do not re-litigate)
- **Laravel Sanctum, SPA cookie (stateful) authentication.** React and API share one origin (`localhost:8080`; production
  uses the real domain), so no tokens in JavaScript. Flow: `GET /sanctum/csrf-cookie` -> `POST /api/v1/auth/login`.
  Configure `SANCTUM_STATEFUL_DOMAINS` and session/cookie settings from env (local + production-friendly; `secure` cookie
  controlled by env). Use `$middleware->statefulApi()`.
- Roles: `admin`, `editor`, `architect`, `user` as a backed PHP enum `App\Enums\Role`, stored in a `role` string column on
  `users` (default `user`). No third-party permission package.
- Abilities (Gates/Policies) — define as constants in one class `App\Support\Ability`:
  `manage-config` (admin, editor), `manage-users` (admin), `review-plans` (admin, architect), `own-plans` (every authenticated role).
  Also a route middleware alias `role:<a>,<b>` that returns the standard 403 problem response (from T0.8).

## Deliverables
1. Install/configure Sanctum (`php artisan install:api` is fine; keep PHP 8.2 compatibility and exact versions).
2. Migration: add `role` (indexed) to `users`; keep the default Laravel columns; `down()` implemented.
3. Endpoints under `/api/v1/auth` (thin controllers + FormRequests + Actions + Resources):
   - `POST register` {name, email, password, password_confirmation}: creates role `user` ONLY (ignore any `role` in payload).
     Password min 10 chars, must not equal the email; email normalised (trim + lowercase); unique; throttle 5/min per IP.
   - `POST login` {email, password}: starts the session; on failure ALWAYS the same 401 `UNAUTHENTICATED` response whether
     the email exists or not (no user enumeration; constant-ish behaviour); throttle 5/min per email+IP -> 429 problem.
     Regenerate the session id on login.
   - `POST logout`: invalidates session, regenerates CSRF token.
   - `GET me`: `{ "data": { id, name, email, role, abilities: [...] } }` — `abilities` computed from the gates, never the password/hash.
4. `database/seeders/DevUserSeeder.php`: creates one user per role (`admin@aihome.local`, `editor@…`, `architect@…`, `user@…`,
   password documented in the seeder + README.local.md, **only when `app()->environment('local')`**; no-op otherwise).
   Call it from `DatabaseSeeder` and expose `make seed`.
5. Document the flow in `docs/api-contract.md` (append a section; this file exists after T0.8) with curl examples that include
   the CSRF/cookie steps.

## Tests (Pest, sqlite in memory, `withoutVite()` where views are involved)
- Register: success (201, role is `user`, password stored hashed, never returned); `role=admin` in payload is ignored;
  duplicate email (case-insensitive: `A@X.com` vs `a@x.com`) -> 422 problem+json; weak/short password; password == email;
  missing/blank fields; email with surrounding spaces is normalised; very long name (> 255) rejected; Japanese name works.
- Login: success sets session and `me` then works; wrong password and unknown email produce IDENTICAL status + body (except request_id);
  session id changes after login; logout then `me` -> 401; `me` without login -> 401 problem+json.
- Throttling: 6th failed login within a minute -> 429 with `Retry-After`; a different email is unaffected; successful login is not throttled.
- Authorization matrix: for each of the 4 roles x 4 abilities assert allow/deny exactly as specified; `role:` middleware allows/denies
  and returns the 403 problem body; an unauthenticated request to a role-protected route gets 401 (not 403).
- Mass assignment: calling the model/`update` with `role` through user-facing paths cannot escalate privileges.
- Seeder: creates 4 users in `local`, creates nothing in `production`, and is idempotent (running twice does not duplicate).
- CSRF: login/logout/register from a stateful origin without the CSRF token -> 419 handled as a problem+json response
  (add a `419`/`CSRF_MISMATCH` mapping to the T0.8 handler if missing, and test it).

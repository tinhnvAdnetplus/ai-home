# TASK T1.2 — JSON Schema export + shared conformance fixtures (TASKS.md row 1.2). TS lane.

Goal: the server (PHP, no Node in production) must validate admin-submitted wizard configs with EXACTLY the same rules as the TypeScript package. Two layers:
1. **Structural rules** -> exported as a JSON Schema generated from the Zod schemas (single source of truth, never hand-written).
2. **Cross rules** (duplicate keys, unknown refs, cycles, binding types, default values, limits, condition depth/node counts) cannot be expressed in JSON Schema. PHP (task T1.4) will
   re-implement them. To guarantee both languages agree WITHOUT Node on the server, this task produces a **golden fixture corpus** that both the TS tests (now) and the PHP tests (T1.4) run.
This task builds the schema artifact, the fixture corpus, the generators, the differential tests and the documentation. No PHP changes.

## Where things live (the api container only mounts `apps/api`, so artifacts PHP must read live inside it)
- Generated schema: `apps/api/resources/config-schema/wizard.schema.json` (committed, deterministic).
- Fixtures: `apps/api/resources/config-schema/fixtures/wizard/<nn>-<slug>.json`, one case per file:
  `{ "name": string, "description": string, "input": <any JSON value>, "expected": { "ok": boolean, "codes": string[] (sorted, unique), "firstPath"?: (string|number)[] } , "structural": "valid" | "invalid", "knownDivergence"?: string }`
  where `structural` says what a plain JSON-Schema validator must answer for `input` (cross-rule-only failures are structurally VALID).
- Source of the fixtures: `packages/config-schema/src/fixtures/*.ts` (builders producing the JSON values; readable, deterministic, no randomness, no timestamps).

## Deliverables
1. **JSON Schema generation** (`packages/config-schema/src/json-schema/`): use `zod-to-json-schema` (exact version compatible with the installed zod 3.24.x) or an equivalent exact-pinned approach; target draft-07
   (widest validator support, incl. PHP `opis/json-schema`). Post-process as needed so recursion (`z.lazy` conditions) becomes `$ref`/`definitions`, objects are strict (`additionalProperties: false`),
   limits that ARE expressible are present (`maxItems` for steps 20 / sections 20 / options 60 and similar, `maxLength`, `minimum`, `pattern`...), `$id`, `title`, and `"x-schemaVersion": 1`. Deterministic output
   (stable key order, 2-space indent, trailing newline). Script `schema:generate` (package.json) writes the file; `schema:check` fails if the committed file differs from a fresh generation.
2. **Divergences must be handled, not hidden.** Zod trims localized texts before checking length; JSON Schema cannot trim. Decide the cleanest contract (e.g. the schema requires a non-whitespace character via `pattern`
   and the server must trim texts BEFORE validating, a documented "normalization step" listed in the docs) and prove it with fixtures. Anything that still cannot match goes in a fixture's `knownDivergence` (must be rare and explained).
   PCRE vs ECMAScript: a plain `$` also matches before a trailing newline in PCRE (PHP) — include fixtures such as a key `"abc\n"` and make sure the pattern/contract rejects it in BOTH engines
   (e.g. use `\z`-safe constructs or an explicit extra constraint); document it for T1.4.
3. **Fixture corpus** (>= 70 cases): the valid sample wizard; at least one case for EVERY issue code (`SCHEMA_INVALID`, `DUPLICATE_KEY` (steps, sections, fields, options, field keys across steps), `UNKNOWN_FIELD_REF`,
   `SELF_REFERENCE`, `CONDITION_CYCLE` (2-cycle and 3-cycle), `UNKNOWN_BINDING`, `BINDING_TYPE_MISMATCH`, `DUPLICATE_BINDING`, `DEFAULT_NOT_IN_OPTIONS`, `DEFAULT_OUT_OF_RANGE`, `RANGE_INVALID`, `SELECTION_LIMITS_INVALID`,
   `EMPTY_OPTIONS`, `LIMIT_EXCEEDED`); each field type valid + invalid; boundary pairs (exactly at / one over) for steps 20, sections 20, fields 150, options 60, ja text 500 chars, condition depth 6/7, nodes 60/61, `in` list 50/51,
   key length 48/49; hostile values (`__proto__`, `constructor`, `prototype` as keys and as `var`, uppercase/hyphen/leading digit keys, keys with trailing newline / NUL / fullwidth letters, text with only whitespace, wrong JSON types:
   number-as-string, null, array-instead-of-object, extra unknown properties, missing required properties, NaN-like strings, very long but legal strings, emoji/Japanese/Vietnamese text, empty `steps`).
   Each fixture's `expected` is produced by running the real `parseWizardConfig` (the generator writes the files), and a test re-parses every file and asserts the stored `expected` still matches (so a behaviour change forces a
   deliberate fixture regeneration + review). Script `fixtures:generate` writes them deterministically; `fixtures:check` verifies they are up to date.
4. **Differential test with a real JSON Schema validator** (`ajv` as a dev dependency, exact version, draft-07, strict mode): for every fixture, `ajv` accepts the input iff `structural === "valid"`. This proves the exported schema equals the
   structural part of the Zod schema on the whole corpus. Report any fixture where it disagrees and resolve it as in item 2.
5. Wire into the toolchain: `make schema` (generate schema + fixtures) and `make schema-check` (both `*:check`), and add `schema-check` to `check-js` and `check`. (This is the only task allowed to edit the Makefile right now.)
6. Docs: `docs/config-schema.md` new section "Cross-language validation contract": what the schema covers, the normalization step, the list of cross rules PHP must implement (with the exact limits and the cycle-detection semantics),
   the fixture format, how to regenerate, and a table of every `knownDivergence`.

## Tests (Vitest, in the package; deterministic, no network/time)
- generation is deterministic (run twice -> identical bytes) and idempotent; committed file == fresh generation; schema is itself a valid draft-07 schema (ajv `validateSchema`).
- every fixture file parses, has the documented shape, unique names, sorted unique codes; `expected` matches the live `parseWizardConfig`; ajv differential for all fixtures; at least one fixture per issue code and per field type (asserted).
- fixture corpus covers all 14 issue codes (assert against `ISSUE_CODES`), so adding a code without a fixture fails.
- the corpus contains no duplicate `input`s and total size < 2 MB.

## Acceptance
`make check-js` exits 0 twice; `make schema-check` exits 0; then ONE final full `make check`. No eslint-disable / any / `as` / skipped tests; files < 150 loc. Sabotage (show failing output, restore): (1) change a limit in the Zod schema without
regenerating -> `schema:check` / up-to-date test fails; (2) loosen the generated key `pattern` -> the ajv differential fails on the hostile-key fixtures; (3) edit one `expected.codes` in a fixture file -> the fixture test fails;
(4) remove one fixture covering an issue code -> the coverage test fails.

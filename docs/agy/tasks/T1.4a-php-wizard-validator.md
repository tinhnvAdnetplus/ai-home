# TASK T1.4a — PHP port of the wizard config validator (PHP lane). Unit tests are DEFERRED (see BRIEF 3-TEMP).

Goal: the server must reject invalid admin-submitted wizard configs with EXACTLY the rules of the TypeScript package `packages/config-schema` (PHP has no Node in production).
Port those rules to PHP now; the shared fixture corpus produced by the TS lane (T1.2, later) will be used afterwards to prove both implementations agree.
The follow-up task T1.4b builds the HTTP endpoints/actions on top of this validator, so keep its API clean.

## Read first (the source of truth to port)
`packages/config-schema/src/**` — `primitives.ts`, `condition.ts`, `condition-types.ts`, `condition-metrics.ts`, `binding-registry*.ts`, `wizard/*.ts` (esp. `wizard-schema.ts`, `field-schemas.ts`, `base-field.ts`, `option-schema.ts`,
`precheck-limits.ts`, `validate.ts`, `cross-validate.ts`, `cycle-detect.ts`, `binding-validator.ts`, `field-validator.ts`, `field-options-validator.ts`, `issue-codes.ts`, `types.ts`), `docs/config-schema.md`, and
`database/` models from T1.3 (`ConfigDocument`, `ConfigVersion`). Port behaviour, limits and issue codes exactly; do not invent new rules.

## Deliverables (namespace `App\Config\Wizard`, files under `app/Config/Wizard/`, all classes `final`, strict types, small files)
1. `ConfigIssueCode` (string-backed enum, identical case names/values to the TS `ISSUE_CODES`) and `ConfigIssue` (readonly value object: `array $path`, `ConfigIssueCode $code`, `string $message`).
2. `WizardConfigValidator::validate(mixed $input): ValidationResult` where `ValidationResult` has `ok`, `issues` (list), `data` (normalized array when ok). **Never throws** for any input (wrap in try/catch Throwable -> a single `SCHEMA_INVALID` issue).
   Order of work, exactly like TS: (a) `LimitPrecheck` (cheap structural limits BEFORE walking anything: steps <= 20, sections per step <= 20, fields total <= 150, options per field <= 60; return on the first violation, cost bounded by the limits not by the input size —
   100k steps must be rejected in milliseconds); (b) structural validation ("strict objects": unknown properties rejected, types checked; JSON-decoded associative arrays, lists vs objects distinguished; no PHP type juggling: `"1"` is not `1`, `true` is not `1`, `null` is not missing);
   (c) normalization (trim of localized texts as the TS schema does) and (d) cross validation reporting ALL issues: duplicate keys, unknown field refs, self reference, condition cycles (DFS, same semantics as TS), unknown binding, binding type mismatch, duplicate binding, default not in options / out of range,
   range invalid, selection limits, empty options, limit exceeded.
3. Primitives: localized text (`ja` required, `en`/`vi` optional, no other keys, length counted in Unicode characters with `mb_strlen`, trimmed, 1..500), `Key` regex `^[a-z][a-z0-9_]{0,47}$` **anchored with `\z` (PCRE `$` also matches before a trailing newline; keys like "abc\n" must be rejected)** plus the same deny-list as TS (`constructor`, `prototype`, `hasownproperty`, `tostring`, `valueof`, `proto` ...),
   binding keys, media refs, step icon allow-list, upload MIME allow-list — all copied from the TS constants (put the shared constants in `WizardConstants` with a comment pointing at the TS file they mirror).
4. Condition AST validator (restricted JSON-Logic subset): operators `and or ! == != < <= > >= in` with exact arity, `{var: key}`, scalar literals (string <= 200 chars, finite numbers, bool, null), depth <= 6, nodes <= 60, `in` right side = var or scalar list <= 50, exactly one key per operator object, no unknown operators.
   Use an explicit work stack or a depth guard: a 50k-level nested input must be rejected without a PHP recursion problem. `ConditionVars::collect()` helper like TS `collectConditionVars`.
5. `BindingRegistry` (PHP constant list of the 39 planner inputs with `key` + `valueType` + `description`, mirrored from `binding-registry-data.ts`) and the field-type <-> value-type compatibility rules from `binding-validator.ts`.
6. Never trust PHP array semantics: JSON objects with numeric-like keys, `__proto__` / `constructor` keys (they are plain strings in PHP but must still be rejected by key rules), integer-vs-float distinctions (1 vs 1.0 vs "1"), very large numbers, NaN/INF cannot come from JSON but can come from PHP callers: reject non-finite floats.
7. Raw-JSON entry point `WizardConfigValidator::validateJson(string $json): ValidationResult` using `json_decode($json, true, 64, JSON_THROW_ON_ERROR | JSON_BIGINT_AS_STRING)`; invalid JSON / too deep / not an object -> `SCHEMA_INVALID`; size cap 1 MB before decoding.
8. Artisan command `config:validate-wizard {file}` (in `app/Console/Commands/`) printing `OK` or one line per issue (`code path message`) and exiting 0/1. Sample files under `apps/api/database/data/validator-samples/`: `valid-sample.json` (port of the TS `sampleWizard` from `src/defaults/sample-wizard.ts` / `sample-steps.ts`)
   and at least 12 small invalid files, one per important issue code (duplicate key, unknown ref, cycle, binding mismatch, default out of range, limit exceeded, key with trailing newline, `__proto__` key, text too long, unknown extra property, wrong type, depth 7 condition).
   These samples are your manual verification and will be reused with the TS fixture corpus later.
9. Document in `docs/api-contract.md` a short "Config validation" section: the issue code table, limits, and that texts are trimmed.

## How to verify (no unit tests now)

Also run it on a generated oversized file (100k steps) and a 50k-deep condition to show it returns fast
(write those two generator files with your write tool or build them via a small artisan option; do NOT use python/node inline scripts). Then `pint --test`, `phpstan analyse` (Larastan level 6), and ONE `vendor/bin/pest` run (existing suites must pass; the arch tests apply to your new classes: strict types, final, no closures in routes, etc.).

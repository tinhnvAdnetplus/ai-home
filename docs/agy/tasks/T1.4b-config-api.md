## Endpoints (all JSON, all under /api/v1)
Public:
- `GET /config/bundle` -> `{ "etag": "...", "configs": { "wizard": { "version": 3, "schemaVersion": 1, "publishedAt": "...", "payload": {...} } } }` containing ONLY published versions (empty `configs` if none). Strong `ETag` header (hash of document keys + published version ids + payload hashes), honour `If-None-Match` with 304 and no body, `Cache-Control: no-cache`. Never exposes drafts, users, audit data.
Admin (`auth:sanctum` + `can:manage-config`; unauthenticated -> 401, other roles -> 403, both as problem+json):
- `GET /admin/configs` -> list of documents: key, scope, current published version number/date, whether a draft exists and its last update.
- `GET /admin/configs/{key}` -> document + published version (with payload) + draft (with payload) if any + the 20 most recent versions (metadata only).
- `PUT /admin/configs/{key}/draft` body `{ "payload": {...}, "label": "optional <=120 chars" }`: validate the payload with the registered validator (422 problem with code `CONFIG_INVALID` and an `issues` array of `{code, path, message}`; payload > 1 MB -> 413); create the draft if none (version = max(version)+1, `based_on_version_id` = current published) or update the existing one. Optimistic concurrency: when a draft already exists the request MUST send `If-Match: <draft etag>` (the draft response carries a strong `ETag`); missing -> 428 `PRECONDITION_REQUIRED`, mismatch -> 412 `PRECONDITION_FAILED`. Concurrent creation of two drafts is caught from the DB unique violation and returned as 409 `CONFLICT`.
- `DELETE /admin/configs/{key}/draft` -> discards the draft (204), audited.
- `POST /admin/configs/{key}/publish` body `{ "label"? }`: inside a DB transaction with `lockForUpdate` on the document row: re-validate the draft payload, mark the previous published version `archived`, turn the draft into the new `published` version (status, `is_draft` NULL, `published_by`, `published_at`, recompute `payload_hash`), set `current_version_id`, write the audit row. Publishing without a draft -> 409/422 problem (`NO_DRAFT`). Publishing an unchanged payload (same hash as the published one) is allowed but flagged in the audit summary.
- `POST /admin/configs/{key}/rollback` body `{ "version": 2 }`: creates a NEW published version copying the payload of that older version (history stays linear, nothing is mutated), re-validates it with the CURRENT validator, archives the previous one, audited with `Rollback`. Unknown version -> 404; rolling back to the already-current version -> 422.
- `GET /admin/configs/{key}/versions` (paginated, newest first, metadata only), `GET /admin/configs/{key}/versions/{n}` (with payload), `GET /admin/configs/{key}/audit` (paginated: action, user id/name, version, summary, request id, created_at).
All state changes write an audit row (`ConfigAuditLog`, with `request_id` from `RequestId`, NEVER IP/user agent). Unknown `{key}` -> 404. `{n}` must be a positive integer (route constraint).

## Design rules
- Thin controllers -> FormRequests -> final Actions (`BuildConfigBundle`, `SaveConfigDraft`, `DiscardConfigDraft`, `PublishConfigDraft`, `RollbackConfig`, `RecordConfigAudit`) -> Resources. Transactions + row locks wherever two requests could race; no check-then-act without a lock.
- New problem codes in `ApiErrorCode` with titles/details and docs: `CONFIG_INVALID` (422, plus `issues`), `PRECONDITION_REQUIRED` (428), `PRECONDITION_FAILED` (412), `CONFLICT` (409), `NO_DRAFT` (422). Extend `ApiProblem` through a dedicated exception carrying the issues (no leaking of internals; the generic 500 behaviour stays).
- Security: payload is data, never executed or rendered as HTML; never log payloads or tokens; mass-assignment guarded (status/hash/publish columns only via `forceFill` inside the Actions); `If-Match` compared with a constant-time check; response bodies never include `password`/hashes of users, only id + name in audit rows.
- Rate limit the admin write endpoints (e.g. 30/min per user) with a named limiter.
- Artisan tooling: `php artisan config:publish-file {key} {file} {--label=}` which validates a JSON file and publishes it (creating the document if needed) through the same Actions, acting as a system user (audit `user_id` NULL). The reviewer will use it to load the default wizard.
- Docs: extend `docs/api-contract.md` (endpoints, headers, examples with the cookie + CSRF flow from the auth section, problem examples for each new code).
